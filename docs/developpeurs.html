💻 Guide du développeur

Tout ce qu’il faut pour travailler sur France·Sim : installer, comprendre l’architecture, savoir où vit chaque chose, et respecter les quelques règles qui gardent le modèle honnête et le jeu jouable.

Démarrer

Prérequis : Node.js 20 ou plus récent. Aucune base de données, aucun serveur : tout tourne dans le navigateur.

npm install
npm run dev        # jeu en développement (Vite, rechargement à chaud), http://localhost:5173
npm test           # tests (Vitest)
npx vitest         # tests en continu
npm run lint       # oxlint
npm run build      # vérification des types (tsc -b) puis build de production dans dist/
npm run check      # lint + tests + build : ce que vérifie GitHub
npm run docs       # régénère docs/catalogue.html et docs/modele.html
Outil Rôle
TypeScript 6Tout le code, en mode strict (variables et paramètres inutilisés interdits).
React 19L’interface. Pas de bibliothèque d’état : l’état vit dans App.tsx et la simulation est recalculée.
Vite 8Serveur de développement et build. Les CSV sont importés avec ?raw : ils sont embarqués dans le build.
Vitest 5Tests, dans src/**/*.test.ts.
oxlintLint, avec les règles React (pas de setState synchrone dans un effet, fonctions pures au rendu…).

Aucune autre dépendance : graphiques, carte des flux, graphe des causes sont en SVG écrit à la main.

Le cycle d’un rendu

Il n’y a pas de « tour » mémorisé : à chaque rendu, App.tsx refait la simulation depuis l’année de départ, avec la liste des décisions et des événements. C’est simple, déterministe, et assez rapide (≈ 0,4 ms par année simulée).

Les concepts à connaître

Paramètres, variantes, scénarios de départ

  • Aucun nombre magique dans le moteur. Chaque coefficient se lit dans P.xxx (comportements), chaque donnée dans BASE.xxx, chaque part par tranche dans GROUP_PARAMS.xxx[g]. Ce sont des getters : ils renvoient la valeur en vigueur.
  • Variante : simulate({ …, params: { vatPassThrough: 0.6 } }) applique temporairement d’autres valeurs (withParams), puis remet celles des fichiers. C’est ce qu’utilisent le cerveau du modèle, l’analyse de solidité et le rejeu.
  • Point de départ : simulate({ …, scenario: { reference, params } }) change l’année de départ, ses données et sa politique de référence (REF dans sim.ts). C’est ainsi que le même moteur rejoue 2000–2024.

Une partie = des décisions et des événements

  • Decision = { year, patch } : à partir de year, les leviers du patch changent. policyAt(decisions, year) donne la politique en vigueur.
  • FiredEvent = { year, id } : un événement et son année ; ses effects s’ajoutent au monde année après année (worldAt).
  • Comparer à « sans rien changer » : la partie (states) et la référence (base) partagent les mêmes événements ; seules les décisions diffèrent.
  • Hasard reproductible : rollEvents(seed, year, …) tire les événements avec une graine par partie. Même graine, mêmes événements.

Une année = step(prev, policy, world, anchors)

  • Carry : ce qui passe d’une année à l’autre (stocks, mémoires : dette, patrimoine, température cumulée, colère…).
  • Anchors : les repères calés sur l’année de départ (revenus « normaux », taux d’impôt implicites).
  • YearState : tout ce que l’interface affiche. La propriété closure doit rester nulle : la somme des soldes de tous les acteurs.

Les règles du projet

  1. Tout coefficient dans un CSV, avec un nom, une explication, une fiabilité, une source ou le mot « hypothèse », et une plage plausible si c’est une hypothèse. Un test refuse un paramètre déclaré mais inutilisé.
  2. Chaque nouveau mécanisme dans le graphe des causes (variables.csv, liens.csv) : c’est ce que les joueurs lisent.
  3. La comptabilité boucle : tout euro versé est reçu par quelqu’un. Une nouvelle dépense publique va dans les biens publics ou dans un transfert existant, une recette dans taxes et sort du revenu de quelqu’un.
  4. Le passé reste reproduit : après un changement du moteur, vérifier le rejeu 2000–2024 (npx vitest run replay).
  5. Le jeu reste jouable : chaque scénario a une stratégie gagnante dans src/game/game.test.ts.
  6. L’interface explique : un nouvel événement a des facteurs de probabilité nommés ; un nouvel indicateur peut entrer dans la fenêtre « Pourquoi ? ».
  7. Textes en français clair, pour des non-spécialistes ; commentaires du code en français, qui disent le « pourquoi ».
  8. React : pas de setState synchrone dans un effet (dériver l’état, ou agir dans un rappel) ; pas d’appel impur au rendu (Math.random, Date.now).
  9. Interface : rien ne doit bouger sous la souris (pas d’explication qui s’ouvre au survol et décale les curseurs) ; tester les fenêtres avec un vrai clic (voir tester l’interface).
  10. Commits : un commit par sujet, avec un message qui dit ce qui change et pourquoi.

Tester l’interface

Les tests automatiques couvrent le moteur et les règles du jeu, pas l’affichage. Pour l’interface, vérifiez dans le navigateur, à plusieurs largeurs (1440, 1200, 1000, 375 px). Pour un bouton dans une fenêtre, assurez-vous qu’il est réellement cliquable : un clic déclenché par programme (button.click()) réussit même sur un bouton caché derrière une autre couche. Dans la console du navigateur : 

const b = [...document.querySelectorAll('button')].find((x) => x.textContent.includes('Prendre les commandes'))
const r = b.getBoundingClientRect()
b.contains(document.elementFromPoint(r.left + r.width / 2, r.top + r.height / 2)) // doit valoir true
