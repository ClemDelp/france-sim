🧪 Tester son changement

Un changement de paramètre peut avoir des effets en cascade. Trois niveaux de vérification, du plus simple au plus complet, vous disent s’il tient debout. Les deux premiers ne demandent aucune installation.

Niveau 1 — Dans le jeu

Dans 🧠 Le modèle → Tous les paramètres, changez une valeur : vous jouez alors avec une variante du modèle.

Outil Où Ce qu’il vous dit
Bandeau de la variante en haut du jeu et du modèle L’effet de votre variante sur la croissance, le chômage, la dette et la pauvreté, l’année en cours, comparé au modèle d’origine.
Face au passé (2000–2024) 🧠 Le modèle → onglet « Face au passé » Le modèle rejoue 2000–2024 avec les décisions réellement prises et le monde tel qu’il a été. La colonne « Avec votre variante » dit si votre valeur reproduit mieux ou moins bien l’histoire (écart moyen par indicateur).
🔬 Ce résultat est-il solide ? verdict d’une idée reçue, onglet Courbes Refait le calcul en faisant varier chaque hypothèse dans sa plage plausible : quelles hypothèses décident du résultat.
🔍 Pourquoi en est-on là ? la une du journal La part de chaque décision et de chaque événement dans la situation de l’année, et l’effet de leur combinaison.
Le graphe des causes 🧠 Le modèle → Graphe Pour une variable, ce qui la fait bouger et ce qu’elle fait bouger, avec les paramètres de chaque lien et leur valeur dans votre partie.

La variante n’est gardée que dans votre navigateur et disparaît au rechargement : c’est un banc d’essai, pas une modification du dépôt.

Niveau 2 — Sur GitHub : les tests automatiques

Dès que vous proposez une modification (pull request), GitHub lance automatiquement toutes les vérifications du projet (fichier .github/workflows/ci.yml). En bas de la page de votre proposition :

  • 🟡 en cours : patientez quelques minutes ;
  • ✅ All checks have passed : le modèle reste cohérent avec votre changement ;
  • ❌ Some checks were not successful : cliquez sur Details, puis sur l’étape en rouge. Le nom du test qui échoue et son message s’affichent ; voir que faire si un test échoue.

Niveau 3 — Sur votre ordinateur

Avec Node.js installé, à la racine du dépôt :

npm install            # une seule fois
npm test               # tous les tests (quelques secondes)
npx vitest             # relance les tests à chaque modification de fichier
npx vitest run replay  # seulement les tests dont le fichier contient « replay »
npm run check          # tout ce que vérifie GitHub : lint, tests, compilation
npm run dev            # le jeu, avec vos fichiers modifiés

Les tests affichent aussi des informations utiles, par exemple l’écart du rejeu 2000–2024 pour chaque indicateur.

Ce que garantissent les tests

Fichier de tests Il vérifie que…
src/model/modele.test.ts Les fichiers sont valides : chaque ligne a le bon nombre de colonnes (pas de « ; » dans un texte), aucun identifiant en double, chaque paramètre a une source ou une fiabilité et est utilisé par le moteur, chaque lien du graphe relie des variables et cite des paramètres qui existent, les parts de la dette font 100 %. Le long terme est stable : jusqu’en 2075, avec ou sans chaque idée reçue, rien ne s’emballe (inflation, chômage, croissance) ; la population vieillit sans s’effondrer.
src/model/sim.test.ts La comptabilité boucle chaque année (ce que l’un paie, un autre le reçoit). La France de 2025 est bien calée. Les grands mécanismes gardent leur sens : taxer les riches réduit la pauvreté, annuler la dette de la BCE ne rapporte presque rien, la retraite à 60 ans coûte, tous les impôts au maximum font perdre la partie, le contrôle des frontières n’arrête qu’une partie des arrivées, l’aide au développement réduit les départs forcés, une armée et une culture fortes accroissent l’influence…
src/model/replay.test.ts Le passé reste reproduit : rejoué de 2000 à 2024, le modèle reste proche de l’histoire (écarts moyens plafonnés), retrouve les récessions de 2009 et 2020 et l’inflation de 2022, et ne déclenche aucune crise imaginaire.
src/model/robustness.test.ts, explain.test.ts L’analyse de solidité et les explications « Pourquoi ? » fonctionnent ; tendance + causes + effet de combinaison redonnent exactement la valeur réelle.
src/game/game.test.ts Le jeu reste jouable : chaque scénario se gagne avec une stratégie connue mais pas en ne faisant rien ; élections, une du journal, conseillers, succès, explication des événements.

Que faire si un test échoue

Un test qui échoue n’est pas forcément une erreur de votre part : il signale que votre changement modifie un comportement que le projet considérait comme établi. Il faut alors décider, ensemble, qui a raison.

Message (extrait) Ce qu’il veut dire Que faire
« chaque ligne a autant de colonnes que l’en-tête » Un « ; » s’est glissé dans un texte, ou une colonne manque. Remplacez le « ; » par une virgule ; comparez la ligne fautive à ses voisines.
« Valeur non numérique dans les paramètres » Une valeur n’est pas un nombre (espace, lettre, deux virgules…). Corrigez la cellule indiquée.
« chaque paramètre est utilisé par le moteur : expected [ 'xxx' ] » Vous avez ajouté (ou renommé) un paramètre que le moteur ne connaît pas. Remettez l’ancien id, ou demandez à un développeur de coder le mécanisme.
« Paramètre « xxx » absent des fichiers du dossier modele/ » Une ligne a été supprimée ou son id modifié. Restaurez la ligne.
« reproduit les grandes lignes de l’histoire » Avec votre valeur, le rejeu 2000–2024 s’éloigne trop de la réalité. Vérifiez l’onglet « Face au passé » : si votre source est solide, discutez-en dans la proposition (le seuil, ou un autre paramètre, est peut-être à revoir).
« reste stable jusqu’en 2075 » Votre valeur fait s’emballer le modèle à long terme (inflation, chômage…). La valeur est souvent hors de sa plage plausible. Essayez-la dans le jeu en avançant jusqu’en 2075.
« ne rien faire ne suffit pas, une bonne stratégie rapporte des étoiles » Un scénario n’est plus gagnable, ou se gagne sans rien faire. Signalez-le : un développeur ajustera les objectifs du scénario (src/game/scenarios.ts).
Un test de mécanisme (« taxing the rich… », « l’aide au développement… ») Votre valeur inverse ou annule un effet attendu. C’est un vrai débat : expliquez votre source. Le test sera adapté si la communauté vous donne raison.

Lire un message vitest : la ligne × donne le nom du test, la ligne AssertionError dit ce qui était attendu (expected … to be less than …), et le chemin du fichier pointe la ligne du test.

Vous ne comprenez pas un échec ? Collez le message dans la discussion de votre proposition : quelqu’un vous aidera.
